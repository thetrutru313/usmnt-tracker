The invoice authorisation fix needs one verification it did not get. Every new
test covers the rejection path; none confirms that a legitimate invoice still
downloads. A fix that over-blocks would pass the whole suite while breaking the
transparency page — which exists specifically so visitors can open invoices
without logging in.

STEP 1 — Check what is actually stored.

Run a read-only query and paste the raw output:

  SELECT id, period_year, period_month, invoice_urls
  FROM transparency_months
  WHERE invoice_urls IS NOT NULL AND invoice_urls::text != '[]';

I need to see the literal `url` values. The new check assumes every one is
exactly "/objects/<suffix>". Report any that are not — full https:// URLs, raw
bucket pathnames like "/bucket-name/uploads/...", or anything else.

This matters because normalizeObjectEntityPath (objectStorage.ts:187-206) has
three return paths and only one produces "/objects/...":
  - input not starting with https://storage.googleapis.com/ → returned unchanged
  - pathname not starting with PRIVATE_OBJECT_DIR → returns the raw pathname
  - otherwise → "/objects/<entityId>"
Whatever it returned is what Admin.tsx line 362 saved. There is also legacy data:
the deleted post-merge.sh backfilled invoice_urls from an older single
invoice_url column, in an unknown format.
