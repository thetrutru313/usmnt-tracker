TASK A — Orphaned fixture_players rows, and the FK that prevents recurrence
═══════════════════════════════════════════════════════════════════

EVIDENCE (production, diagnostic Q18): 8 rows in fixture_players reference
player_id = 23, which no longer exists in players. All 8 carry club_id = 300
(Atletico Madrid). Six of the eight fixtures have no other valid link.

WHY IT MATTERS: fixture_players.player_id has NO foreign key
(schema/fixtures.ts:45), so the rows survived the player's deletion. The
fixtures visibility filter (routes/fixtures.ts:234) tests
EXISTS (SELECT 1 FROM fixture_players ...) — which these rows satisfy — while
the chip query (queries.ts:382) INNER JOINs players and finds nothing. Result:
four upcoming La Liga fixtures render as permanently empty cards.

They cannot self-heal. Every cleanup path in the codebase —
purgeOrphanedUpcomingFixtures, purgeStaleOrphanedPastFixtures, and
purgeStaleTransferredPlayerLinks — tests NOT EXISTS or joins players, so a
fixture whose only link is an orphan looks correctly tagged to all of them.

THE MIGRATION, IN THIS ORDER (the FK will fail if orphans remain):

  1. DELETE FROM fixture_players fp
      WHERE NOT EXISTS (SELECT 1 FROM players p WHERE p.id = fp.player_id);

     Write it generically like that. Do NOT hardcode player_id = 23 or a
     count of 8 — dev may hold a different set, and the same statement must
     be correct in both databases.

  2. Add the foreign key: fixture_players.player_id -> players.id

     NO ON DELETE CASCADE. Use the default (NO ACTION / RESTRICT). Nothing in
     production code deletes players — only test files do — so this row set
     was created by a manual deletion. A restricting FK makes the next manual
     deletion fail loudly instead of silently orphaning links. That is the
     desired behaviour.

  3. Update lib/db/src/schema/fixtures.ts line 45 so playerId carries
     .references(() => playersTable.id), matching fixtureId on line 44.

REPORT the row count deleted in dev, and separately in production after
Publish.

TASK B — Two unique indexes on player_stats
═══════════════════════════════════════════════════════════════════

player_stats currently has only a non-unique index on player_id
(schema/stats.ts:46). Two different invariants need enforcing, because the
table holds two different kinds of row.

B1 — the general key. Diagnostic Q16 confirmed ZERO rows block this:

    UNIQUE (player_id, period_type, season)

    Covers season_all and national_team_cycle, which legitimately hold one
    row PER SEASON YEAR per player (replaceSeasonHistoryRows,
    playerStatsSync.ts:529-535). Multiple rows there are correct.

B2 — the stronger key, for the single-row period types:

    UNIQUE (player_id, period_type)
      WHERE period_type IN ('season','previous_season','last5','previous5')

    upsertStatsRow (playerStatsSync.ts:494-500) deletes scoped by periodType
    ALONE, deliberately not by season — the comment at :495-499 explains that
    the season label for these rows can shift between runs, so filtering the
    delete by the new label would strand the old row. So these four types
    hold exactly ONE row per player regardless of label, and B1 alone would
    not enforce that: it would happily permit a 2025 and a 2026 'season' row
    for the same player.

    Pre-flight already done: diagnostic Q1 grouped by (player_id, period_type)
    and found duplicates ONLY in season_all and national_team_cycle. These
    four types are clean, so B2 can be created without cleanup. Confirm this
    holds on dev before generating, since dev may carry test residue.

Use a partial unique index for B2 — the same pattern already used at
schema/stats.ts:90-92 for match_logs and at schema/clubs.ts for
api_football_team_id.

DO NOT add UNIQUE (player_id, period_type) unqualified. It would reject the
legitimate multi-season season_all rows and destroy the club-season selector.

TASK C — Deterministic read in the form-badge query
═══════════════════════════════════════════════════════════════════

computeFormBadgesForPlayerIds (queries.ts:106-134) selects last5/previous5/
season rows with no ORDER BY, no LIMIT and no dedup, then folds them into a
Map with plain .set() at :130-133 — so with more than one matching row the
last one Postgres happens to return wins, arbitrarily.

Two hundred lines away, getStatsForPlayer (queries.ts:207-214) — which feeds
the numbers rendered directly beneath the badge — does
.orderBy(desc(createdAt)).limit(1). The two disagree by construction.

BE HONEST ABOUT THE PRIORITY: after Task B2 this is belt-and-braces, because
duplicates for those period types become impossible at the database level. Do
it anyway — the query should not depend on a constraint added elsewhere for
its correctness — but do not describe it as a live bug fix. Diagnostic Q15
confirmed zero disagreeing duplicates in production today.

Make the read explicitly deterministic: order by created_at descending and
take the newest row per (player_id, period_type), matching what
getStatsForPlayer already does.
