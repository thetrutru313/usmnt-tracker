Prompt 13 — Recover the Prompt 12 deploy

CONTEXT: Publishing Prompt 12 failed validation. The FK statement
  ALTER TABLE "fixture_players" ADD CONSTRAINT "fixture_players_player_id_players_id_fk"
could not be applied, because production still holds 8 orphaned
fixture_players rows (all referencing deleted player_id 23).

ROOT CAUSE — this is the important part:

Replit's Publish flow does NOT execute our migration files. It computes a
SCHEMA DIFF between dev and production and generates DDL from it. The publish
dialog listed exactly five statements — the FK, two CREATE UNIQUE INDEX, two
DROP COLUMN. Our migration 0002 begins with:

    DELETE FROM "fixture_players" fp
    WHERE NOT EXISTS (SELECT 1 FROM "players" p WHERE p.id = fp.player_id);

That statement was absent. A schema diff cannot express DML, so any DELETE,
UPDATE or backfill written into a migration file NEVER reaches production.

This is why 0000_baseline and 0001_add_admin_sessions appeared to work — both
were pure DDL, so the diff produced equivalent statements. Prompt 12 is the
first migration that depended on data changes crossing over.

NOTHING WAS APPLIED. The publish failed validation before executing, so
production is untouched. Do not re-attempt the publish until this is resolved.

STEP 3 — Correct the documentation
═══════════════════════════════════════════════════════════════════

lib/db/README.md currently implies migration files are the production source
of truth. They are not. Rewrite that section to state plainly:

  - Migration files are authoritative for DEV only.
  - Production receives a SCHEMA DIFF computed by Replit's Publish flow
    between the dev and production schemas. Migration files are not executed
    there.
  - Therefore DDL crosses over; DML does NOT. Any data repair — DELETE,
    UPDATE, backfill — must ship as application code that runs at startup,
    be verified in production, and then be removed.
  - A schema change that DEPENDS on a data change must be split across two
    publishes, in that order. Document this recovery as the worked example.
  - Because the diff reads DEV's schema, dev drifting from the migration
    files means production inherits dev's shape, not the repo's. Never run
    drizzle-kit push against dev.

Also add a note to CHECKPOINT.md under the schema-management section.
