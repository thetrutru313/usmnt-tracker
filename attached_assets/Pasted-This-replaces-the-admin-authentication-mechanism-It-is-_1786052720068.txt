────────────────────────────────────────────────────────────────────────
THE PROBLEM
────────────────────────────────────────────────────────────────────────

After login, the browser stores the admin password ITSELF in localStorage and
sends it as `Authorization: Bearer <password>` on every admin request
(artifacts/usmnt-tracker/src/pages/Admin.tsx, saveSession and authHeaders).

This is not a session token. There is no server-side session at all —
POST /admin/transparency/verify confirms the password and returns a number
telling the browser how long to pretend the session lasts.

Consequences: any script that can read localStorage on our origin obtains the
permanent admin password, not a revocable session. Logging out clears the
browser but invalidates nothing. The password cannot be revoked without
changing an environment variable and redeploying. Expiry is a browser-side
courtesy an attacker ignores.

SCHEMA MECHANICS — read before writing any code
────────────────────────────────────────────────────────────────────────

This adds a table, and the schema deployment path has changed since this
prompt was first written. See lib/db/README.md.

  - `drizzle-kit migrate` is authoritative. NEVER use `push` against dev or
    production.
  - NEVER point `migrate` at production. Production has no drizzle schema; it
    would try to create all existing tables.
  - Production receives schema through Replit's Publish flow, which is
    confirmed working — it carried six indexes in Prompt 4.

So the sequence is: edit the schema files, generate a migration, apply it to
DEV with migrate, commit, and let Publish carry it to production.

DEPLOY ORDERING RISK — the one thing most likely to go wrong here.

If the application code deploys before the admin_sessions table exists in
production, every admin request fails. Two mitigations, do both:

  a. The requireAdminSession middleware must handle a MISSING TABLE gracefully.
     If the query fails because the relation does not exist, return 503 with a
     clear message — the same shape used today when ADMIN_PASSWORD is unset —
     rather than a 500 stack trace. Add a test for this.
  b. After Publish, verify the table exists in production before assuming the
     feature works. I will run the Publish; you verify afterwards.

Also state a rollback: if admin access breaks in production, what is the exact
recovery? Reverting the commit and republishing should restore the old
password-as-token path, since the table being present is harmless to it.
Confirm that reasoning holds.

────────────────────────────────────────────────────────────────────────
WHAT TO BUILD
────────────────────────────────────────────────────────────────────────

The pattern already exists in this codebase — recovery_tokens and the flow in
routes/follows.ts do exactly this correctly. Copy that approach; do not invent
a new one.

1. New table `admin_sessions`: id, token_hash (SHA-256, unique), created_at,
   expires_at, revoked_at. Use lib/db/src/schema/recoveryTokens.ts as the
   template. Index token_hash.

2. POST /admin/transparency/verify: on correct password, generate a token with
   generateToken() from lib/tokenUtils.ts, store its hash with an expiry driven
   by ADMIN_SESSION_HOURS (default 24), return the plaintext once. Never again.

   KEEP the rate limiter added in Prompt 1 (5 requests per 15 minutes, applied
   BEFORE the password check). transparencyVerifyRateLimit.test.ts asserts the
   6th request returns 429 — that test must still pass.

3. New middleware requireAdminSession: read the Bearer token, hash it, look up
   a non-revoked, non-expired row. Follow the shape of requireAnonUser in
   lib/anonAuth.ts. Handle the missing-table case per (a) above.

4. Switch every admin surface to the new middleware — routes/admin.ts,
   routes/transparency.ts, routes/storage.ts, routes/schedule.ts. Find them
   yourself rather than trusting this list; grep for ADMIN_PASSWORD.

   ADMIN_PASSWORD remains the LOGIN credential only. It must stop being the API
   credential.

5. POST /admin/logout — sets revoked_at on the current session.

6. Expired-session cleanup: add it to the existing sweep in
   lib/anonUserCleanup.ts rather than introducing another timer.

7. Frontend: update Admin.tsx and AdminReviewQueue.tsx to store the returned
   session token instead of the password. Their session-handling code is
   currently near-identical duplication — extract it into one shared module
   while you are there. Handle 401 by clearing local state and showing login.

8. Preserve current behaviour when ADMIN_PASSWORD is unset: admin routes return
   503, not 500.
