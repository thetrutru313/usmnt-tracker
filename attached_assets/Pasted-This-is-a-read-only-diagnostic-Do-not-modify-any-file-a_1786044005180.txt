3. THE DECISIVE TEST — do the migration files reproduce reality?
────────────────────────────────────────────────────────────────────────

This single question determines which path 4B takes.

You need a throwaway database. In order of preference:

  a. NEON BRANCH. Production is Neon-backed. If you can reach the Neon project
     directly, branch production — an instant copy-on-write clone. Best option:
     real schema, real data, disposable, zero risk to the original.
  b. createdb usmnt_scratch. May fail if Replit's managed Postgres does not
     grant CREATE DATABASE to the app role. Try it; report the error if so.
  c. A separate SCHEMA in the development database. Create schema "scratch",
     set search_path, work there. Fiddlier but equivalent for this purpose.

Report which you used and why. Do NOT skip this test — it decides whether 4B
needs a baseline at all, and guessing wrong is expensive.

Apply ONLY the existing migration files, in filename order, using raw psql —
not drizzle-kit push, which would bypass the files and defeat the test:

  for f in lib/db/drizzle/*.sql; do psql "$SCRATCH_URL" -f "$f"; done

Report every error. A file failing to apply IS the answer.

Then compare against PRODUCTION (not development — production is what we are
baselining for):

  pg_dump "<production url>" --schema-only --no-owner --no-acl | sort > /tmp/prod.sql
  pg_dump "$SCRATCH_URL"     --schema-only --no-owner --no-acl | sort > /tmp/scratch.sql
  diff /tmp/prod.sql /tmp/scratch.sql

Report the diff in full, then state which case applies:

  CASE A — the files reproduce production exactly.
    Good outcome. 4B only needs to reconcile the journal and the applied-
    migrations table. No baseline required.

  CASE B — they do not.
    Expected, since `push` has been the real deployment mechanism. List every
    difference: missing tables, columns, indexes, type mismatches. This is what
    a baseline has to capture.

5. THE STAGED INDEX MIGRATION
────────────────────────────────────────────────────────────────────────

Run this against BOTH databases and report each result separately:

  SELECT indexname, tablename FROM pg_indexes
  WHERE schemaname = 'public'
    AND indexname IN (
      'player_stats_player_id_idx','injuries_player_id_idx',
      'fixtures_kickoff_idx','players_club_id_idx',
      'news_article_players_article_id_idx','news_article_players_player_id_idx'

This matters more than it looks. Those six indexes are in the schema FILES, so
any baseline generated from the schema will include them — and if that baseline
is then marked already-applied, the indexes would never actually be created.
4B applies them first for exactly this reason, but it needs to know the true
starting state in each database.
