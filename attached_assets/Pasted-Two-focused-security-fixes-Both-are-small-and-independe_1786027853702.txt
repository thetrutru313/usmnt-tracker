Two focused security fixes. Both are small and independently testable. Do not
refactor anything else while you are in these files.

FIX 1 — Brute-force protection on the admin login endpoint.

File: artifacts/api-server/src/routes/transparency.ts
The route POST /admin/transparency/verify at line 109 has no dedicated rate
limiter. Only the global 300-requests-per-minute limiter from app.ts applies,
which permits roughly 18,000 password guesses per hour from one IP.

Add an express-rate-limit limiter allowing 5 requests per 15 minutes per IP,
applied to that route only. Follow the existing pattern in
artifacts/api-server/src/routes/follows.ts lines 19-25 — same library, same
options shape, same style of explanatory comment. Return a clear JSON error
message on limit.

FIX 2 — Authorisation on invoice downloads.

File: artifacts/api-server/src/routes/transparency.ts, route
GET /transparency/invoice/*objectPath at line 78.

Right now this takes whatever path the caller supplies, prefixes it with the
private storage directory, and returns a signed download URL. There is no
check that the requested object is actually a transparency invoice. Any file
in the private bucket is retrievable by anyone who learns its path.

THIS IS CONFIRMED, NOT THEORETICAL. During an earlier verification task, this
request succeeded with no Authorization header:

  curl -s -o /dev/null -w "%{http_code}" --max-redirs 0 \
    "http://localhost:8080/api/transparency/invoice/uploads/<some-uuid>"
  → HTTP 302, with a valid signed storage URL in the Location header

Note that "uploads/<uuid>" is the raw internal storage layout produced by
getObjectEntityUploadURL — not a path derived from any transparency record.
Use that exact request shape as your regression test.

Before signing, verify the requested objectPath appears in the invoice_urls
JSONB column of some row in transparency_months. If it does not, return 404
with the existing "Invoice not found" message — do not leak the difference
between "not an invoice" and "does not exist". Keep the endpoint public for
paths that ARE valid invoices; that is intentional per the existing comment.

TESTS — add both:
- A test asserting the 6th login attempt within the window returns 429.
- A test asserting GET /transparency/invoice/ with a path not present in
  transparency_months returns 404 and never calls the signing function.

Put them alongside the existing transparency tests in
artifacts/api-server/src/lib/__tests__/. Mock @workspace/db the same way the
neighbouring test files do.

VERIFY: pnpm run typecheck && pnpm --filter @workspace/api-server run test

Report the diff and the test results. Do not touch admin authentication
itself — that is a later, larger task.
